# MetalTask product and engineering specification

**Status (2026-11-13).** The repository started at `85c846f` with an MIT license. The bootstrap provides a Swift 6 package, a SwiftUI window, and a library for physical memory and default Metal device information. Live sampling, process attribution, graphics footprint, model inspection, and release packaging are planned. See [TODO.md](TODO.md) for verification and the next work item.

## Product and platform

MetalTask helps someone investigating a local Mac answer three questions: is the GPU busy, which visible processes are contributing, and what can macOS tell us about their graphics memory? The next release after core telemetry should help local AI users understand which models are loaded and how model weights, cache, and runtime overhead might explain memory use.

Start with Apple Silicon, Swift 6 language mode and SwiftUI. The package deployment target is macOS 14, a provisional floor until tested on actual hardware. Validate the oldest supported macOS and a current release on at least two Apple Silicon generations before claiming broad support. Intel and non-Metal machines can display available system information with explicit capability states. Intel, eGPU and multi-adapter telemetry are outside the initial support claim. Keep the app read-only, local and usable as a standard user. Process termination, host monitoring, a menu bar view, long-term recording and export are outside the initial release.

[macmon](https://github.com/vladkens/macmon) already offers Apple Silicon hardware monitoring and a process list with GPU metrics in a terminal UI, plus programmatic output. [SiliconScope](https://github.com/kennss/SiliconScope) offers a native Apple Silicon dashboard, a process inspector and AI workload integrations. MetalTask should earn its place through a GPU-first workflow: one ranked view of visible GPU processes, clear graphics-memory accounting and coverage, and a process or runtime inspector with evidence for each figure. Validate that workflow with a Metal benchmark and a local AI workload before adding general sensor dashboards.

## Telemetry contract

| Signal and UI label | Proposed source and semantics | Fallback |
| --- | --- | --- |
| Default GPU, unified memory, recommended working set | Public Metal APIs. Working set is Apple's approximate performance guidance for allocations. | Show system RAM and explain when Metal or the working-set value is unavailable. |
| Physical memory | `ProcessInfo.physicalMemory`. Total installed memory visible to macOS. On Apple Silicon CPU and GPU share a pool. | Independent of GPU counters. |
| GPU activity | Device-wide driver-reported percentage from `IOAccelerator` → `PerformanceStatistics` → `Device Utilization %`, after validation. The driver's averaging interval may be unspecified. | Gap in chart, with reason and last sample age if useful. |
| Driver-reported GPU allocations | Candidate `Alloc system memory` on the selected accelerator. Verify unit and accounting scope before display. | Omit the number when the schema or interpretation is unknown. |
| Process GPU activity | Derive accumulated GPU time per elapsed wall time from observable AGX clients. Coverage and normalization must be explicit. | A recognized client can appear as “GPU client detected” with an unavailable rate. If enumeration fails, show attribution unavailable and keep independent device metrics. |
| Graphics footprint | Candidate dirty bytes charged to graphics categories by `/usr/bin/footprint` for a readable process. Verify categories, units and permissions before exposing a number. | Show “Permission denied,” “Unavailable,” or “Stale” as applicable. |
| Process memory, if added | OS process memory with its own definition and label, such as physical footprint. | Keep this optional and independent of graphics footprint. |

Apple's [IORegistry API](https://developer.apple.com/documentation/iokit/1514293-ioregistryentrycreatecfproperty) is documented. The driver classes, keys and schema above are implementation details. [Metal working-set guidance](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize), [unified memory](https://developer.apple.com/documentation/metal/mtldevice/hasunifiedmemory) and [Metal resource allocation size](https://developer.apple.com/documentation/metal/mtldevice/currentallocatedsize) have distinct scopes. `currentAllocatedSize` covers resources allocated by the calling app on its Metal device. Driver allocations, installed RAM, process footprint, model file size and runtime-reported memory answer different questions. Shared allocations, incomplete visibility and accounting differences prevent reconciling process rows to a device total. A dedicated VRAM gauge would misrepresent Apple Silicon.

### Native collection and compatibility

- Enumerate relevant services with IOKit and extract typed fields from Core Foundation values. Release iterators and services, adopt retained CF values once, and convert them to Swift values before crossing an actor boundary. Match telemetry to an unambiguous accelerator. If multiple candidates cannot be linked to the default Metal device, surface the ambiguity. Decode only expected numeric types, reject booleans, overflow and invalid ranges, and accept partial snapshots.
- Probe capabilities at launch and after sleep, wake or service replacement. Keep IOKit and driver-specific decoding behind a provider. Treat absent keys as unavailable, stale samples as aged, and malformed values as schema failures. Use `ioreg` for development probes and fixture capture. If a shipping fallback is needed, evaluate a bounded plist-mode `ioreg` adapter only after confirming that it produces equivalent readings when direct access fails. Retain static Metal info and explicit unavailable states if neither source works.
- For per-process activity, investigate `AGXDeviceUserClient` → `IOUserClientCreator` and `AppUsage[].accumulatedGPUTime`, with `IORegistryEntryID` as the client identity. Upstream reports nanoseconds. Confirm units and sampling behavior on our target systems. Resolve owner, name and process start time with `libproc` where readable, using AppKit's running app metadata to enrich labels. Validate identity before applying asynchronous results. A PID is reusable and app metadata covers only part of the process population.
- Diff each stable client for the same device and process identity using a monotonic clock. Aggregate valid client deltas over the interval per process. New clients, disappearing clients, PID reuse, reset counters, invalid or excessive elapsed intervals and wake require fresh baselines or partial coverage. Never reuse an enumeration index as a persistent ID. Work from short-lived clients may go unobserved. If there is no comparable baseline, show an unavailable rate. A known valid delta of zero is idle for the observed clients and interval. Concurrent clients or engines can overlap. Expose `GPU time / elapsed time` with its units and coverage until tests justify a bounded utilization percentage. Never normalize to a 100% pie or silently clamp overlapping time.
- Gate footprint by process eligibility and capability. Same-user reads are candidates and may still fail for protected processes. Other-user and system processes often require privileges, and OS protections may still apply. Probe without elevation, using a known-owned test process and a controlled permission test. Schedule footprint separately from the 1 s activity sampler. Start with one worker, selected and active rows first, a 5 s minimum interval per active process, 30 s for idle rows and a 3 s command timeout. Revalidate PID plus start time around the call. Distinguish an absent category in a validated complete result from missing or unrecognized output. Ship zero only when the parser and workload tests establish that the result means zero.
- Call `/usr/bin/footprint` directly with numeric PID arguments, using a private unique temporary directory and a size-bounded JSON file if supported by the observed OS. Drain subprocess output with bounds, terminate and reap on cancellation or timeout, and clean up on every exit path. Limit retries and back off on repeated denial. Omit this provider from a release if cost, permissions or parsing remain unreliable.

Candidate driver fields and footprint categories are documented by [gputaskman's macOS backend](https://github.com/shanselman/gputaskman/blob/main/src/gputaskman/macos.py). Those observations provide leads and a comparison baseline. MetalTask must validate its own implementation.

## Package and data flow

- `MetalTask` is the SwiftUI executable. Keep selection, filters, presentation and formatting here. Use a `@MainActor` observable window model with one sampling subscription. Render a device summary, optional Swift Charts history with gaps, a sortable process table and a detail pane. Default to sorting by observed activity. Unavailable values sort last in either direction. Keep selection keyed by process identity across refreshes. Show source, age and coverage in the inspector and make status readable with VoiceOver and without color.
- `MetalTelemetry` is a reusable Swift package target. It owns value types, collectors, parsing and aggregation, with no SwiftUI dependency. Start with one device provider and add independent process and footprint providers when their validation passes. Inject a clock and fixture provider for deterministic tests. Keep types internal until a public use case needs them.
- Use an actor to own sampling state, client baselines and a bounded in-memory history. Start with one sample per second and 120 history points per metric. Publish immutable `Sendable` snapshots through a stream buffered to the newest update. Slow providers run off the main actor with bounded work and no overlapping scans. Cancel when the last consumer leaves, stop while asleep, and reset baselines on resume. Isolate driver, process and footprint failures so they can recover independently.
- Proposed data contract: each snapshot carries monotonic time, display timestamp, device identity and provider capability. Each metric carries optional typed value, unit, source and scope, capture time, and evidence (`observed`, `derivedFromCounters`, `runtimeReported`, `estimated`, or `fixture`). Track freshness, coverage and unavailable reason independently. A process row uses PID and start time, with an explicitly transient identity if start time is unavailable. Transient rows cannot inherit history or asynchronous enrichment. Store bytes as integer values and validate arithmetic before converting for display.
- Add `ModelInspection` as a separate target once the core contract is stable. It will produce asynchronous enrichment keyed by runtime or confirmed process identity. Basic collection must keep working with model inspection disabled or unavailable.

For development UI work, use a visibly labeled fixture preview. A sanitized capture from a pinned `gputaskman --json` version can supply a comparison fixture if useful. Do not map a generic VRAM or GPU field from that output until its macOS meaning is confirmed. There is no Python runtime dependency in the initial package or proposed release.

## Local AI inspection

1. **Ollama.** Start with an opt-in, local-only [GET /api/ps](https://docs.ollama.com/api/ps) integration. Show model identity, quantization, loaded context when supplied, and the runtime's reported sizes with their source. Keep a server-level “Loaded models” list until there is corroborated evidence connecting a runner PID and start time to a specific model. The API response alone cannot establish that join. Version-tolerant decoding must accept missing fields, multiple models and empty responses. Poll independently with timeouts and backoff.
2. **MLX.** Recognize probable MLX workloads only from explicit evidence. Prefer an opt-in cooperative reporter or user-selected model/config metadata. If a cooperative process reports allocator figures, distinguish its active, cached and peak values. A Python name, model file or memory-map hint cannot establish which model is active or its allocator usage. Support an identified runtime with model unknown.
3. **llama.cpp.** Start with metadata-only reading of a user-selected [GGUF](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md) file. Extract architecture, tensor metadata and quantization if known. Account for split files explicitly. An optional user-enabled [local llama-server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server) integration can provide corroborating runtime metadata. Loaded context, GPU layer offload and cache placement remain unknown without runtime evidence.
4. **Estimates.** Put weights and KV-cache estimates beside their inputs, sources and caveats. For a supported dense attention layout, estimate KV capacity from allocated token slots × layers with attention × KV heads × head width × (bytes per K element + bytes per V element), adjusting for actual runtime allocation, block formats and alignment where known. Require enough metadata to select a formula. Account for parallel contexts according to the runtime's allocation model. Sliding-window, hybrid, quantized cache and offload configurations need independent rules or an unavailable estimate. File size includes metadata and possibly padding, and differs from resident weights. Scratch buffers and allocator overhead remain unknown without evidence. Never infer these components by subtracting them from a process footprint or label a calculated total as measured.

## Security, privacy and distribution

The regular app runs without elevation, a privileged helper, Full Disk Access prompts, background uploads, or process modification. Never collect command lines, environments, prompts or model contents by default. Keep process names and model identifiers in memory and omit them from logs by default. Diagnostics are explicit, previewable and redacted of paths, user names, PIDs, model identifiers and secrets. Avoid raw registry and footprint dumps in issues and test fixtures.

An enabled model integration makes read-only requests to a fixed loopback endpoint with no proxy, redirects, cookies or shared credential cache. Bound time, response size and request frequency. Verify transport behavior in tests, including redirects and proxy settings. Treat all response and file data as untrusted. Bound file and field lengths, counts, nesting, offset arithmetic and read volume. Restrict file inspection to user-selected regular files and avoid following untrusted paths from model metadata. Never execute or load a selected model to identify it.

Use a conventional macOS app bundle for distribution via GitHub Releases outside the Mac App Store. Keep hardened runtime enabled and start with the minimum entitlements required for a regular unsandboxed app. Package an arm64 build, choose a stable bundle identifier, sign with Developer ID Application, notarize with Apple's tools, staple the ticket, and test Gatekeeper and a fresh standard-user install from the downloaded release. Use the app bundle when testing telemetry access under release conditions. Publish checksum, license notices and a support matrix with each release. [Apple notarization workflow](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
